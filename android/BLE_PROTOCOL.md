# 感知板到手机的 BLE 数据协议 1

App 0.2.0 实现本协议的中心端。当前感知板固件 1.3.5 只有手表心率客户端，尚未实现这些服务；本文件是后续固件的配合契约，不代表已经完成实板连接。

手机通过 BLE 读取感知板的环形 CSV 快照，再复用现有解析、Room 和 HTTPS 上报。上报配对码、采集凭证和主机登录信息不经过 BLE。蓝牙地址和板端启动标识仅用于本机连接/去重，不加入上传行或公开来源名称。

## GATT

| 项目 | UUID | 属性 |
| --- | --- | --- |
| 数据服务 | `9f8d0001-7b6a-4b61-8d0f-0ac49f8a0001` | 广播必须包含此服务 |
| INFO | `9f8d0002-7b6a-4b61-8d0f-0ac49f8a0001` | Read |
| DATA | `9f8d0003-7b6a-4b61-8d0f-0ac49f8a0001` | Notify，含标准 CCCD |
| CONTROL | `9f8d0004-7b6a-4b61-8d0f-0ac49f8a0001` | Write with response |

固件维持现有手表中心端，同时提供一个手机外设连接。INFO 可以公开读取；CONTROL 与 DATA/CCCD 必须要求加密、系统配对及绑定，保留绑定密钥。App 在确认服务和型号之后请求系统配对；不能只依靠设备名称识别兼容性。

INFO 是不超过 512 字节的 UTF-8 JSON，例：

```json
{"model":"FIREFLY-SENSE N16R8","ble_protocol":1,"board_id":"board-A"}
```

`board_id` 在同一块板上稳定；标识只能使用 1–64 位字母、数字、点、下划线或连字符。广播地址须可用于绑定后重连；若采用地址隐私，须保留系统可解析的绑定身份。手机连接后发现服务、读取 INFO、完成绑定、启用 DATA 通知，再开始请求。

## 快照

CONTROL 命令恰好 5 字节：第一字节 `0x01`，后四字节是非零 uint32 请求编号，使用小端序。这可以放入最小 ATT 负载。单连接只允许一个未完成请求，固件不会在没有请求时持续发送数据。

固件先原子地复制当前环形缓存，并捕获同一时刻的 `uptime_ms`。最多 256 行（现有 HTTP 环形缓存上限 200 行）。按顺序通过 DATA 发送以下 JSON 行，每行以 LF 结束：

```json
{"v":1,"type":"begin","request_id":7,"uptime_ms":6000,"boot_id":"boot-A","rows":1}
{"v":1,"type":"row","request_id":7,"csv":"CSV,1000,..."}
{"v":1,"type":"end","request_id":7,"rows":1}
```

- 所有消息带同一请求编号，`v` 必须为整数 1。`boot_id` 每次整板启动改变，在这次启动期间不变；格式同 `board_id`。
- `uptime_ms` 为 uint32，行是原有 schema 5 CSV，包含 CH6 心率。发送失败时不得伪造 `end`。
- 每条 JSON 行最多 4096 字节，CSV 最多 2048 字符。依据协商后的 MTU 按字节分片，每个通知不超过 MTU−3；UTF-8 字符也可能跨片。串行发送，不能交错快照。
- 开始发送的时间应靠近快照复制时间；缓慢发送时仍使用原先的 uptime。手机收到 begin 时保存对应手机时间，所有行按此锚点恢复采样时刻。
- `end.rows`、`begin.rows` 和实际收到的行数须一致。空快照为 begin/end、rows=0。
- 手机仅接受完整快照，超时、错误顺序、缺片和超限时断开，下一轮重新连接并请求当前环形缓存。旧请求编号不会被当成本轮响应。

App 每轮完成读取、缓存和上传后等待 5 秒。蓝牙采集不会向板子确认服务器已存储，板子也不能因此清除环形缓存；手机的 HTTPS 确认仍只清除 Room 中匹配的上报事件。环形缓存不是无限历史，长时间离开板子仍可能错过早期样本。

## 验证边界

App 自动测试覆盖碎片重组、最小 MTU 分片、错误顺序/计数/版本、UTF-8、缓存边界和 CH6 解析。后续固件需要实际验证手机与手表同时连接、系统配对、锁屏、重启、蓝牙关闭/重开、断线重连和缓存补传。
